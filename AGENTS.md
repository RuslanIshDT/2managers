# 2managers — инструкции разработчику-LLM

Отдельный самостоятельный проект. Правила, процессы и документы других проектов
на него не распространяются; из них берётся только то, что прямо назовёт владелец.

Название — 2managers (владелец переименовал 27.11.2026, было ecompras). Прежнее имя остаётся в технических метках, по которым находятся уже созданные данные: папка на сервере, база и пользователь PostgreSQL, тома и контейнеры Compose, метка ecompras в Langfuse и в заголовках запросов к модели, префикс задач Трекера, календарь стенда, Message-ID и UID писем и встреч. Их не переименовывать: метку ecompras и бота владелец оставил (27.11.2026).

## Любой агент
- Правила одни для всех инструментов и моделей и живут только здесь. Файлы CLAUDE.md, GEMINI.md, .cursor/rules/agents.mdc, .github/copilot-instructions.md, .aider.conf.yml — только указатели на этот файл, правил в них не писать.
- Инструмент не подхватил правила сам — начать с фразы «Прочитай AGENTS.md».
- Порядок чтения перед работой: этот файл, docs/contest.md, docs/criteria.md, docs/tz.md, docs/architecture.md, docs/backlog.md. На сервере ещё _not_in_git/LOCAL.md (стенд и доступ; в репозиторий не переносить).
- Договорённости хранить в этих файлах, а не в памяти инструмента или чате: следующий агент их не увидит.

## Работа
- Ветка одна — main: изменения идут сразу в неё.
- Перед работой проверить git status; чужие незакоммиченные изменения не перезаписывать.
- Стек — ниже, менять и добавлять только решением владельца. Версии фиксируются при первой сборке.
- Где допустим хардкод (решения владельца 26.11.2026, docs/tz.md, «Уровень исполнения»): в частях «минимально» и «заглушка» — экраны задач, календаря и рассылки протокола, HR-коннектор (файлы вместо системы), второй руководитель файлом, правки списком — хардкод и кликабельный фронт допустимы, если так и названы в форме и бэклоге. В ключевом — агенты и механизмы K1–K15 — хардкода нет: id, имён и чисел из синтетики (p02, m062, «Ольга», 10%) в их коде нет, всё берётся из данных руководителя; сцену для демо готовим данными, а не кодом. Проверка ключевого: новое письмо, которого нет в синтетике, и второй руководитель с другими людьми.

## Стек (принят владельцем 25.11.2026)
- Язык: TypeScript, front и back в одном репозитории.
- Front: React + Vite, Tailwind, shadcn/ui.
- Back: Node.js 24 + Fastify (API, вызовы модели, раздача front), Zod (общие схемы), SSE для вывода ответа модели.
- База: PostgreSQL 17, Drizzle (схема и миграции), pg-boss (очередь долгих задач).
- Вход: сессии в базе, пароли через scrypt из Node.
- Модели: только с back через один модуль, Kodik Router (решение владельца 27.11.2026; утром 27.11 был OpenRouter); у каждого агента своя модель — настройка. Учёт стоимости и трассировка — Langfuse (решение владельца 26.11.2026, S1 и L1–L5 в docs/tz.md).
- Файлы: Docker volume. Запуск: Docker Compose, nginx с HTTPS впереди.
- Тесты: Vitest, Playwright.
- Интеграции: реально — Яндекс Почта и Telegram (бот владельца). Трекер и Календарь Яндекса подключаем (владелец 27.11.2026, T43), Телемост не подключаем. Живой видеоаватар не делаем.
- Векторный поиск не используем: поиск по полям в PostgreSQL, обоснование — docs/architecture.md, раздел 5 (решение исполнителя по поручению владельца 26.11.2026).

## Требования и задачи
- docs/tz.md — постановка заказчика дословно и требования из неё (R, W, M, D, S, E). Менять только от вводных владельца; чего нет в тексте — «вопрос», не додумывать.
- docs/backlog.md — задачи T: «Сейчас» (одна), «Далее» (по порядку), «Сделано». Других списков задач не заводить.
- Задачу владельца занести строкой в бэклог. Вопрос задавать, только если без ответа можно сделать не то.
- Порядок задач определяет владелец. Коммит — с номером задачи: «T3: …».

## Конкурс
Проект делается на 48-часовой конкурс: 26.11.2026 10:00 – 28.11.2026 12:00 МСК (срок сдачи перенесён организаторами 26.11.2026, было 10:00).
Требования к сдаче и что делать по каждому полю — в docs/contest.md; прочитать перед работой.

- Форма сдачи — form/form.json, страница /form на стенде показывает её как есть. Другой копии не заводить.
- Начиная задачу, назвать поля формы (их id), на которые она работает. Если таких нет — сказать об этом владельцу.
- Закончив задачу, в том же изменении обновить в form.json её поля: value, done, left, status и updated (время МСК).
- Любые изменения коммитить и отправлять в main сразу, без отдельного подтверждения (разрешил владелец 26.11.2026). Границы ниже это не отменяет.
- В отчёте владельцу указать по затронутым полям: что сделано, что частично или на заглушке, что не сделано.
- Писать только проверенное. Не проверено — в left. Заглушку называть заглушкой.
- status: todo — нечего сдавать; partial — есть часть; done — value можно отправлять как есть, left пуст.
- Поле без звёздочки тоже вести. Тексты title, hint и требования организаторов не менять.
- Страница и репозиторий публичные: тестовый доступ, ключи и адреса в form.json не вносить. Адрес стенда подставляется сам через {{origin}}.
